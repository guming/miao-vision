# Trusted Interactive Report PRD

> Status: Proposal
> Date: 2026-08-03
> Owner: Miao Vision CLI
> Scope: interactive data reports generated by `miao-viz`
> Related: `miao-viz-interactive-runtime-prd.md`, `evidence-lineage-coverage-prd.md`, `report-intelligence-knowledge-prd.md`

## 1. Summary

Miao Vision already supports self-contained interactive HTML reports with select and range filters, chart selection, detail tables, drilldown, reset, view-state links, and deterministic browser-side recomputation. The remaining product gap is not basic interactivity. It is whether an agent can generate an interactive report that a creator can safely hand to a business reader without exposing unnecessary data or mixing conclusions from different data scopes.

This PRD turns the existing runtime into a trusted delivery workflow built around three capabilities:

1. Minimize embedded data and protect sensitive fields.
2. Let `data analyze` recommend a safe interaction plan that agents can instantiate without designing interactions from scratch.
3. Separate verified published findings from deterministic summaries of the reader's current filtered view.

The product promise is:

> Give an agent a local data file and receive an offline interactive HTML report that embeds only necessary data, can be safely handed to a business reader, and clearly distinguishes published conclusions from current-view calculations.

## 2. Product Decision

### 2.1 Recommended direction

Build one trusted-interaction contract consumed by the analyzer, interaction planner, validator, artifact packager, runtime, and renderer. Deliver it in three independently mergeable phases:

1. Safe Artifact Packaging.
2. Agent Interaction Planning.
3. Trusted View Scopes.

Each phase must improve an existing report workflow even if later phases never ship.

| Capability | Owning phase | Release outcome |
|---|---|---|
| Data minimization and sensitive-field protection | Phase 1 | The creator can inspect exactly what the HTML embeds and receives an aggregate share-safety decision |
| Agent-generated interaction plan | Phase 2 | The agent selects a deterministic, validator-ready preset from analyze context |
| Published/current-view trust separation | Phase 3 | The reader can explore filtered data without mistaking local calculations for verified findings |

### 2.2 Why this is one PRD

The three capabilities share one data boundary:

```text
Local Dataset
      │
      ▼
data analyze
  ├─ fields and semantics
  ├─ evidence
  ├─ sensitivity signals
  └─ interaction recommendations
      │
      ▼
Agent / interaction instantiate
      │
      ▼
Report Spec
  ├─ global filters
  ├─ detail fields
  ├─ embedded-data policy
  └─ current-view summaries
      │
      ▼
spec validate --context --verify --strict
      │
      ▼
Artifact Packager
  ├─ minimal embedded rows
  ├─ exposure manifest
  └─ published evidence
      │
      ▼
Offline HTML Runtime
  ├─ filters and drilldown
  ├─ published findings
  └─ current-view summaries
```

Separate PRDs would allow the planner to recommend fields that the packager must reject, or allow the runtime to display filtered calculations beside full-dataset insights without a shared scope contract.

### 2.3 Relationship to the existing runtime PRD

`miao-viz-interactive-runtime-prd.md` remains the source for the fixed offline runtime, filter controls, chart selection, drilldown, and browser-side rendering. Its MVP is partially implemented. This PRD owns the additional product and safety contract required to call the result safe to share.

This PRD applies only to data reports. Browser decks keep their current runtime and schema. A later initiative may reuse these contracts after they have been validated in reports, but this initiative does not add deck interaction planning, deck data policies, or deck `shareSafe` status.

## 3. Goals

### 3.1 Product goals

- Embed only the fields and rows required by declared interactions.
- Make the embedded-data boundary explicit and machine-readable.
- Prevent agents from automatically selecting sensitive fields for filters or detail views.
- Generate interaction recommendations from analyzed field semantics and user intent.
- Keep interaction specs short, deterministic, and validator-fixable.
- Preserve verified published findings while making their full-dataset scope visible.
- Compute current-view summaries deterministically from active filters.
- Keep generated artifacts local, offline, and self-contained.

### 3.2 Success metrics

1. Trusted mode embeds zero undeclared fields.
2. Every interactive artifact reports embedded fields, row count, byte count, policy, and risks in a structured exposure manifest.
3. Agent-generated interaction specs pass strict validation on at least 27 of the minimum 30 eligible golden fixtures on the first attempt.
4. The planner recommends restricted fields as filters or details in 0% of golden fixtures.
5. Browser current-view results exactly match CLI QueryRecipe results for the same filters in all golden fixtures.
6. When filters are active, 100% of published insights are visibly identified as full-dataset findings.
7. Chromium and WebKit `file://` E2E tests cover filter, drilldown, reset, URL-state restoration, empty results, and print behavior without console errors.

## 4. Users and Jobs

### 4.1 Report creator

The creator uses an agent or the CLI to turn a local CSV, TSV, XLSX, or JSON file into an HTML report. They need to know whether the artifact is safe to hand to another person and should not need to understand interaction implementation details.

Jobs:

- Ask for a report that can be filtered by business dimensions or time.
- Ask for safe detail rows behind a chart.
- Review what data will be embedded before sharing.
- Receive structured warnings when safe delivery is not possible.

### 4.2 Business reader

The reader opens a local HTML file without installing Miao Vision, logging in, or connecting to a server.

Jobs:

- Filter the report by region, product, status, or period.
- Click a chart to inspect allowed detail fields.
- Understand whether a statement describes the full published dataset or the current filtered view.
- Reset the report and reproduce a shared view.

### 4.3 Agent and automation workflow

The agent consumes machine-readable recommendations and validation output.

Jobs:

- Select an applicable interaction preset.
- Instantiate a valid interaction fragment.
- Repair structured validation errors.
- Deliver the artifact only when `shareSafe` is true, or clearly report why review is required.

## 5. Product Principles

### 5.1 Artifact exposure is not input access

The CLI may read the full local dataset, but the generated artifact must embed only the data required for its declared reader experience.

### 5.2 Explicit permission for detail data

A detail view is an intentional disclosure boundary. Chart selection or drilldown must not implicitly authorize embedding every input column.

### 5.3 Sensitivity detection is a guardrail, not proof

High-confidence detection can prevent unsafe automatic choices and require review. Failure to detect a sensitive field must never be presented as a guarantee that the dataset contains no sensitive information.

### 5.4 Published and current-view facts are different products

Published findings are verified against generation-time evidence. Current-view summaries are deterministic local calculations over the active filtered rows. The UI and metadata must never present the two as equivalent.

### 5.5 Agents select presets, not JavaScript

The CLI owns interaction rules and runtime code. Agents select and parameterize validated presets.

### 5.6 Safe fallback over surprising behavior

When the CLI cannot safely embed detail data or calculate a dynamic view, it must remove the affected interaction or return a structured error. It must not silently embed more data or fabricate a current-view conclusion.

## 6. Non-Goals

- Dashboard builder or arbitrary layout editor.
- Arbitrary cross-filter interaction graphs.
- Browser SQL editor.
- Default DuckDB-WASM runtime.
- Database connectors, live refresh, or multiple data sources.
- Login, permissions, cloud sharing, or collaboration.
- Agent-generated browser JavaScript.
- Dynamic natural-language insight generation in the browser.
- Scenario simulation or what-if modeling.
- Encryption or access control for the HTML file.
- A claim that sensitivity detection finds all confidential data.
- Replacing the existing evidence and provenance system.

## 7. Shared Contracts

### 7.1 Trusted artifact status

An interactive render returns one aggregate share-safety result after schema parsing succeeds:

```json
{
  "interactive": true,
  "shareSafe": true,
  "shareSafety": {
    "status": "safe",
    "policy": "detail-safe",
    "embeddedFields": ["region", "order_month", "product", "sales"],
    "excludedFields": ["customer_email"],
    "embeddedRows": 840,
    "embeddedBytes": 138421,
    "risks": [],
    "checks": [
      { "id": "data_policy", "status": "passed", "issues": [] },
      { "id": "sensitivity", "status": "passed", "issues": [] },
      { "id": "artifact_budget", "status": "passed", "issues": [] },
      { "id": "interaction_spec", "status": "passed", "issues": [] },
      { "id": "published_evidence", "status": "passed", "issues": [] },
      { "id": "current_view_recipes", "status": "passed", "issues": [] }
    ]
  }
}
```

`shareSafe` can be true only when:

- an explicit data policy is present;
- no restricted field is embedded;
- the artifact is below the hard size limit;
- the interaction spec passes validation;
- published evidence passes verification when context is supplied;
- every current-view recipe passes validation.

Schema parsing remains fail-fast because later checks cannot safely interpret an invalid document. After parsing, the validator executes every independent share-safety check and returns all issues in deterministic check order. Each issue contains `code`, `path`, `message`, and `severity`; each check has status `passed`, `review`, or `restricted`. Overall `status` is the highest observed severity: `safe`, `review`, or `restricted`; `shareSafe` is true only when every check has status `passed`.

### 7.2 Trust scopes

The product recognizes two scope names:

| Scope | Meaning | Status in this PRD |
|---|---|---|
| `published` | Verified against generation-time evidence and the complete published dataset | Required |
| `current_view` | Deterministically calculated from active browser filters | Required in Phase 3 |

### 7.3 Structured results

All new commands and validation paths preserve the existing result contract:

```json
{ "ok": true, "value": {} }
{ "ok": false, "code": "...", "message": "...", "patches": [], "repairs": [] }
```

`--strict` activates the trusted-report contract; it does not promote every warning to an error. In strict mode:

- an absent `dataPolicy`, including `LEGACY_FULL_ROW_EMBEDDING`, is an error and returns `ok: false`;
- schema, restricted-field, hard-budget, invalid-interaction, invalid-recipe, and failed-evidence conditions return `ok: false`;
- soft-budget, explicit `review` fields, and explicit `full` policy conditions remain warnings, return `ok: true`, and force `shareSafe: false` with overall status `review`;
- a render intended for third-party delivery is complete only when validation returns `ok: true` and `shareSafe: true`.

Without `--strict`, legacy specs remain renderable under the compatibility rules in Section 8.7, but they cannot claim trusted status.

## 8. Phase 1: Safe Artifact Packaging

### 8.1 User value

Creators can inspect and control what the HTML contains before sharing it. Existing filters and drilldowns no longer imply full-row disclosure.

### 8.2 Data policy schema

Add an explicit policy below `interactions`:

```yaml
interactions:
  dataPolicy:
    mode: detail-safe
    detailFields:
      - order_id
      - product
      - sales
    excludeFields:
      - customer_email
      - phone
```

Supported modes:

| Mode | Embedded data |
|---|---|
| `minimal` | Only fields required by filters, chart encodings, transforms, and current-view recipes |
| `detail-safe` | Minimal fields plus explicitly authorized `detailFields` |
| `full` | Every input field; must be explicit and always produces a high-risk disclosure warning |

Rules:

- New generated specs default to `minimal`.
- `detailFields` is valid only with `detail-safe`.
- `select: detail` and detail-producing drilldowns require at least one `detailField`.
- `excludeFields` always wins unless an excluded field is a required dependency, in which case validation fails.
- The packager must never restore excluded fields silently.

### 8.3 Field dependency closure

The packager deterministically collects fields from:

- `interactions.globalFilters[].field`;
- chart encoding channels;
- transform input, group, measure, sort, and filter fields;
- drilldown source fields;
- `dataPolicy.detailFields`;
- current-view recipes;
- renderer-required identifiers explicitly declared by a preset.

The embedded field set is:

```text
required dependency closure
+ explicitly authorized detail fields
- excluded fields
```

Derived transform outputs are not treated as source columns. Their source dependencies are embedded and the fixed runtime derives the output.

### 8.4 Sensitivity signals

Phase 1 uses deterministic, high-confidence signals:

- field-name patterns such as email, phone, mobile, address, credential, token, secret, password, national identifier, and card number;
- `role: id`;
- applicable `semanticTags`;
- near-unique free-text fields;
- explicit user or spec classification.

Near-unique classification is deterministic. For a string field with at least 20 non-null values, `distinctCount / nonNullCount >= 0.95` marks the field `review` unless a stronger rule marks it `restricted`. A field with `role: id` is excluded from automatic filters and detail fields regardless of cardinality. Explicit authorization may admit a `review` field, but never a `restricted` field, in trusted mode.

Classification:

| Level | Behavior |
|---|---|
| `safe` | Eligible for automatic embedding according to policy |
| `review` | Can be embedded only when explicitly requested; emits warning |
| `restricted` | Cannot be automatically recommended or embedded in trusted mode |

False negatives remain possible. The artifact disclosure UI must say what was embedded, not claim the entire source dataset is safe.

### 8.5 Exposure manifest

The renderer returns and embeds a manifest containing:

- data-policy mode;
- embedded and excluded field names;
- embedded row count;
- embedded JSON and total artifact byte counts;
- sensitivity findings;
- review or restriction reasons;
- whether detail rows were sampled or truncated;
- final `safe`, `review`, or `restricted` status.

The HTML exposes a compact reader-facing entry such as “Embedded data details,” while technical fields remain collapsed by default.

### 8.6 Validation errors and warnings

Required codes:

| Code | Severity | Meaning |
|---|---|---|
| `INTERACTION_DATA_POLICY_REQUIRED` | strict error | Trusted interactive output lacks an explicit policy |
| `INTERACTION_DETAIL_FIELDS_REQUIRED` | error | Detail interaction has no authorized detail fields |
| `INTERACTION_EMBEDDED_FIELD_RESTRICTED` | error | Trusted output would embed a restricted field |
| `INTERACTION_EMBEDDED_FIELD_REVIEW` | warning | Explicit field requires creator review |
| `INTERACTION_EXCLUDED_FIELD_REQUIRED` | error | An excluded field is required by the spec |
| `INTERACTION_FULL_DATA_POLICY_EXPOSURE` | warning / review | Full-row embedding was explicitly selected |
| `INTERACTION_ARTIFACT_TOO_LARGE` | warning / review at soft limit; error / restricted at hard limit | Artifact exceeds a budget defined in Section 12.4 |
| `LEGACY_FULL_ROW_EMBEDDING` | warning | Legacy interaction spec has no explicit data policy |

Errors include JSON Patch hints only when there is one safe deterministic repair. A restricted field must not be replaced with a guessed alternative through an automatic patch.

### 8.7 Compatibility

- Existing specs without `dataPolicy` remain readable and render with current behavior.
- They emit `LEGACY_FULL_ROW_EMBEDDING` and cannot return `shareSafe: true`.
- Strict trusted rendering rejects an absent policy.
- New examples, block/template outputs, and Skill guidance always emit an explicit policy.
- Static reports are unchanged.

### 8.8 Phase 1 acceptance criteria

- Excluded field names and values do not appear in the embedded runtime JSON.
- `minimal` embeds the complete dependency closure and no unrelated source columns.
- Detail tables cannot access undeclared fields.
- Full mode displays a high-risk disclosure warning.
- Interactive reports receive real size warnings; interactive mode no longer bypasses artifact budgeting.
- The 10,000-row reference fixture with two filters and eight detail fields becomes interactive within 1 second and updates within 200 milliseconds after a filter change.
- The 50,000-row stress fixture updates within 500 milliseconds after a filter change or produces a deterministic budget fallback before rendering.
- Existing static snapshots remain unchanged.
- Phase 1 can ship without Phase 2 or Phase 3.

## 9. Phase 2: Agent Interaction Planning

### 9.1 User value

Creators ask for an explorable report in natural language. The agent consumes deterministic recommendations instead of inventing field choices and interaction wiring.

### 9.2 Context location

Add recommendations to the existing catalog rather than creating a new top-level context array:

```json
{
  "catalog": {
    "interactions": [
      {
        "preset": "filter-and-detail",
        "score": 0.91,
        "filters": [
          {
            "field": "region",
            "type": "select",
            "reason": "Low-cardinality business dimension"
          },
          {
            "field": "order_month",
            "type": "range",
            "reason": "Valid monthly time field"
          }
        ],
        "detailFields": ["order_id", "product", "sales"],
        "dataPolicy": "detail-safe",
        "risks": []
      }
    ]
  }
}
```

Compact context extends the existing `context-compact.ts` codec with this tuple shape:

```ts
type CompactInteractionRecommendation = [
  preset: 'filter' | 'filter-and-detail',
  score: number,
  filters: Array<[field: string, type: 'select' | 'range', reason: string]>,
  detailFields: string[] | null,
  dataPolicy: 'minimal' | 'detail-safe',
  risks: string[],
]
```

The full and compact forms must round-trip without information loss through the existing codec; no parallel compact-context implementation is introduced. Tuple encoding is already the codec convention for fields, evidence, recommendations, blocks, templates, scenes, and deck patterns, so this contract follows an established pattern rather than adding a second encoding style. Analyze returns at most two interaction recommendations, and their compact UTF-8 serialization must not exceed 2 KB in the default context fixture.

### 9.3 Initial presets

#### `filter`

Applicable when:

- the dataset has a low-cardinality business dimension or valid time field;
- the user intent requests comparison, segmentation, filtering, or time exploration;
- no detail disclosure is needed.

Output:

- at most two global filters;
- `dataPolicy.mode: minimal`;
- no detail fields;
- tooltip enabled on applicable charts.

#### `filter-and-detail`

Applicable when:

- there is a valid selectable dimension;
- safe and useful detail fields exist;
- the intent asks to inspect records, orders, products, or other details;
- artifact size remains inside the allowed budget.

Output:

- at most two global filters;
- one detail-producing chart interaction;
- `dataPolicy.mode: detail-safe`;
- no more than eight authorized detail fields.

Eight fields is the initial reader-usability and performance guardrail: it keeps the detail table scannable and defines the upper-bound fixture used for the 200 millisecond filter target. It is not a permanent schema limit. A later release may raise the planner default after browser benchmarks and reader testing, while the artifact budget remains authoritative.

What-if simulation, arbitrary cross-filter graphs, and custom interaction code are not presets in this phase.

### 9.4 Deterministic filter selection

Scoring factors:

- intent match;
- field role and semantic tags;
- type compatibility;
- cardinality;
- missing-value risk;
- sensitivity level;
- whether the field already participates in the selected report block;
- interaction capability of the target charts.

Rules:

- Prefer time, status, geo, and low-cardinality dimensions.
- Default to at most two filters.
- Never automatically select restricted fields, identifiers, or unrestricted free text.
- `select` is preferred for 2 to 30 distinct values.
- Higher cardinality fields may use searchable select only when explicitly supported and receive a lower score.
- `range` is valid only for numeric and date fields.
- Ties are resolved deterministically by score, field role priority, then field name.

### 9.5 Deterministic detail selection

Rules:

- Every detail field must be `safe`, or explicitly authorized when classified `review`.
- Use `chartUsage.asDetailKey` when present.
- Include the selection dimension and at least one decision-relevant measure.
- Include at most eight fields.
- Do not automatically include free text, contact information, credentials, or near-unique identifiers.
- An identifier can be included only through explicit authorization.
- If no useful safe detail set exists, recommend `filter` instead of `filter-and-detail`.
- The eight-field cap is subordinate to the artifact budget. The planner first removes lower-priority detail fields, then falls back to `filter`; it never exceeds the hard budget to preserve eight fields.

### 9.6 CLI command

Add one command that consumes the catalog recommendation:

```bash
miao-viz spec interaction instantiate filter-and-detail \
  --context context.json \
  --output interactions.yaml
```

Success output includes:

- generated interaction fragment;
- selected recommendation score;
- assumptions and reasons;
- embedded-field preview;
- share-safety warnings.

Failure output includes:

- a structured not-applicable code;
- missing field roles or safety conditions;
- clarification questions only when user choice is genuinely required.

The command must not run a second planner. It materializes an existing `catalog.interactions` recommendation.

### 9.7 Phase 2 fixtures

The golden corpus contains at least 30 eligible cases: five sales, five product analytics, five finance, five operations, three high-cardinality, three sensitive-source, two filter-only because no safe detail set exists, and two with no eligible interactions. Representative expectations include:

| Fixture | Expected recommendation |
|---|---|
| Sales | Region select, month range, order detail |
| Product analytics | Platform select and date range; no user-level sensitive detail |
| Finance | Period range; account-level fields blocked or marked review |
| Operations | Status select and safe ticket detail |
| High cardinality | No ordinary select recommendation |
| Sensitive source | Sensitive fields absent from filters and details |
| Filters eligible, detail unsafe | `filter` recommendation with no detail fields |
| No eligible fields | No recommendation with structured reasons |

### 9.8 Phase 2 acceptance criteria

- Eligible-fixture recommendation coverage is at least 27 of 30 cases.
- First-attempt strict validation pass rate is at least 27 of 30 cases.
- Restricted-field recommendation rate is 0%.
- Default recommendation contains no more than two filters and eight detail fields.
- Compact/full context round-trip preserves recommendations.
- The command produces no JavaScript and no renderer-specific implementation details.
- Phase 2 can ship with the existing runtime even if Phase 3 is not implemented.

## 10. Phase 3: Trusted View Scopes

### 10.1 User value

Readers can distinguish verified findings about the complete published dataset from calculations based on their current filters. Filtering a chart cannot silently change the apparent meaning of a static insight.

### 10.2 Published findings

Existing report insights are `published` by default.

Rules:

- They remain bound to generation-time evidence and provenance.
- The runtime never rewrites them from filtered browser rows.
- When no filter is active, they appear normally.
- When a filter is active, they remain available but are visually de-emphasized and labeled “Based on the full published dataset.”
- Their evidence drawer states that active runtime filters are not part of the published evidence.

### 10.3 Current-view summary schema

Add deterministic summaries below `interactions`:

```yaml
interactions:
  currentView:
    summaries:
      - id: filtered_sales
        label: Current sales
        recipe:
          measures:
            - field: sales
              op: sum
              as: value
        format: currency
      - id: filtered_rows
        label: Current records
        recipe:
          measures:
            - field: "*"
              op: count
              as: value
        format: integer
```

Rules:

- Reuse QueryRecipe as the only calculation contract.
- The browser runtime implements the same supported recipe semantics as the CLI.
- Agents cannot supply arbitrary formulas or JavaScript.
- Current-view summaries are numeric or categorical deterministic summaries, not free-form generated prose.
- Every source field is part of the Phase 1 dependency closure.
- Unsupported recipes fail validation before rendering.

Initial supported summaries:

- record count;
- sum, average, minimum, and maximum of one measure;
- top category by one measure;
- active time range.

### 10.4 Reader experience

Base view:

```text
Published findings
Verified against the full published dataset

Current view
Full dataset · 1,240 rows
```

Filtered view:

```text
Current view
East · 2026-01 to 2026-06
Sales: ¥3.2M
Orders: 840

Published findings
The findings below describe the full published dataset and do not change with filters
```

Rules:

- Active filters, filtered row count, and total row count are always visible.
- Current-view values display `Calculated locally` rather than `Published verified`.
- Empty views show “No data for current view,” not a misleading zero.
- Missing values, invalid divisions, and unavailable comparisons have explicit states.
- Reset clears global filters, chart selection, drilldown and detail state, URL state, charts, and summaries, returning the report to the complete dataset.
- Restoring URL hash state restores the same summaries.

### 10.5 Evidence drawer behavior

For published objects, the drawer shows:

- published evidence IDs;
- source fields and recipes;
- validation rule;
- full-dataset scope;
- a note that active runtime filters were not applied.

For current-view summaries, the drawer shows:

- active filter values;
- filtered and total row counts;
- QueryRecipe;
- source fields;
- local calculation status;
- no claim that the result passed generation-time evidence verification.

### 10.6 System copy and localization

All trusted-interaction system copy comes from a fixed runtime copy catalog rather than scattered renderer strings. Phase 3 ships `en` and `zh-CN` entries for scope labels, exposure status, empty states, calculation status, and print scope. An optional report-level `locale` accepts only `en` or `zh-CN` and defaults to `en`; an unsupported value fails schema validation. This is a scoped runtime catalog, not a claim that the CLI already has general-purpose internationalization infrastructure.

### 10.7 Print behavior

Phase 3 provides two explicit print actions so printing can match either the reader's current view or the verified publication scope:

- `Print current view` is the primary action when filters or drilldown are active. Its header lists active filters and says `Calculated locally`.
- `Print full published report` is always available. A nearby disclosure says active filters and drilldown will not affect that printout.
- The print header says `Full published report`.
- Printing uses a print-only full-dataset view and does not mutate the reader's active on-screen filters.
- Published findings and evidence appendix remain available.
- Neither action requires a server or changes the saved HTML artifact.

When no filter or drilldown is active, the default action is `Print full published report` because that is the scope against which published findings were verified. If the runtime cannot render either print scope without visibly changing on-screen state, Phase 3 is not complete.

### 10.8 Phase 3 acceptance criteria

- Browser summaries exactly match CLI QueryRecipe output under identical filters.
- Every filtered view labels published findings as full-dataset findings.
- Empty, one-row, missing-value, and invalid-calculation cases have explicit UI states.
- URL hash restoration produces identical filters and current-view summaries.
- Evidence UI never calls current-view values generation-time verified evidence.
- Current-view print output reproduces active filters, drilldown scope, visible summaries, and filtered row count.
- Full-scope print output identifies itself as the full published report.
- Phase 3 can ship without what-if simulation or current-view PDF export.

## 11. Validation and Repair

Validation order:

1. Parse report schema.
2. Validate interaction capabilities and fields.
3. Build embedded-field dependency closure.
4. Apply sensitivity and data-policy rules.
5. Validate current-view QueryRecipes.
6. Validate evidence and provenance.
7. Calculate share-safety status and artifact budget.

Patch hints are allowed for:

- adding a deterministically inferred `minimal` policy;
- removing a duplicate filter;
- changing range to select when field type makes that the only valid choice;
- adding a field already required by the chosen chart to the minimal dependency set.

Patch hints are not allowed for:

- replacing or exposing a sensitive field;
- selecting detail fields on behalf of the creator when multiple safe choices exist;
- switching to `full` policy;
- inventing a current-view recipe.

## 12. Testing Strategy

### 12.1 Unit tests

- Field dependency closure.
- Excluded/required-field conflicts.
- Sensitivity classification.
- Data-policy normalization.
- Interaction recommendation scoring and deterministic tie-breaking.
- Detail-field eligibility.
- Compact/full context round-trip.
- Current-view QueryRecipe execution.
- Scope state transitions.
- Structured validation errors and patch hints.
- Artifact budget for interactive HTML.

### 12.2 Workflow tests

Every trusted fixture runs:

```text
data analyze
→ spec interaction instantiate
→ spec validate --context --verify --strict
→ render report
→ inspect shareSafety and exposure manifest
```

Required workflow cases:

- Safe minimal report.
- Safe detail report.
- Restricted detail field rejected.
- Excluded required field rejected.
- Legacy spec renders with warning but is not share-safe.
- Oversized artifact returns review or failure status.
- Filtered summary matches QueryRecipe.

### 12.3 Browser E2E

Tests open the artifact through `file://` in Chromium and WebKit:

- Change select and range filters.
- Confirm KPI, chart, and table updates.
- Select a mark and inspect declared detail fields.
- Confirm restricted fields do not occur in embedded JSON or rendered HTML.
- Confirm published/current-view scope labels.
- Reset all state.
- Copy and reopen URL hash state.
- Exercise empty results.
- Confirm reset clears filters, selection, drilldown, detail rows, URL state, charts, and summaries.
- Print the current view and the full published report; confirm each scope label and row count.
- Assert no page errors or failed runtime initialization.

### 12.4 Performance fixtures

The reference environment is a local `file://` artifact in the current stable Chromium on a machine with at least four performance-class CPU cores and 16 GB RAM, with DevTools closed and the local file cache warm. Report the median of five runs.

Measure at least:

- 1,000 rows;
- 10,000 rows;
- 50,000 rows;
- high-cardinality strings;
- eight declared detail fields;
- two active global filters.

Record:

- artifact bytes;
- embedded JSON bytes;
- initial runtime setup time;
- filter-to-render latency;
- peak browser memory when available.

Release targets:

- The 10,000-row fixture with two filters and eight detail fields reaches first interactive state within 1 second.
- Its median filter-to-render latency is at most 200 milliseconds.
- The 50,000-row stress fixture has median filter-to-render latency of at most 500 milliseconds.
- The compact interaction recommendation payload is at most 2 KB in the default analyze fixture.

The artifact soft and hard byte limits implement the `artifact_budget` share-safety check from Section 7.1 and the `INTERACTION_ARTIFACT_TOO_LARGE` outcomes from Section 8.6. They must be frozen in implementation from these measured fixtures, not copied from the existing static-artifact budget. Crossing the soft limit yields a warning and `review`, then triggers deterministic detail-field reduction or `filter` fallback. Crossing the hard limit yields an error and `restricted`, makes `shareSafe` false, and prevents trusted delivery.

## 15. Rollout and Compatibility

### 15.1 Rollout

- Phase 1 first exposes warnings without changing legacy render success.
- New generated specs use explicit policies immediately.
- Trusted `shareSafe` status is opt-in through explicit policy and strict validation.
- After one minor release, Skill workflows require trusted mode for artifacts intended for third-party sharing.

### 15.2 Rollback

- All new spec fields are additive.
- Static rendering remains available through `--no-interactive`.
- Planner recommendations can be removed without changing existing report specs.
- Current-view summaries can be omitted while filters and published findings continue to work.
- No source data or report run history is migrated.

## 16. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| False confidence from sensitivity detection | Describe embedded fields and risks; never claim complete PII detection |
| Agent chooses too many interactions | Fixed presets, deterministic limits, strict validator |
| Compact context grows substantially | Tuple encoding and explicit size regression tests |
| Browser and CLI calculations drift | Shared QueryRecipe fixtures and equivalence tests |
| Interactive HTML becomes too large | Minimal projection, detail-field limit, artifact budgets, structured fallback |
| Published findings appear to react to filters | Explicit scope model and browser E2E assertions |
| Existing specs rely on full rows | Compatibility warning; no `shareSafe` status until policy is explicit |
| Runtime modules exceed size limits | Split planner, packager, sensitivity, scope, and runtime responsibilities |

## 17. Key Assumption

This PRD assumes creators will accept an explicit data-sharing policy in exchange for a trustworthy `shareSafe` guarantee.

To keep the normal workflow low-friction, agents should automatically select `minimal` when no detail disclosure is requested. When detail data is requested, the CLI can recommend safe fields but must require explicit authorization for fields classified `review`. It must never fall back to embedding the full dataset automatically.

If this assumption proves false, the product must preserve safe defaults and simplify policy authoring. It must not weaken the sharing boundary.

## 18. Definition of Done

The trusted interactive report initiative is complete when:

- all three phases meet their independent acceptance criteria;
- trusted HTML embeds only declared fields;
- an agent can instantiate and validate an interaction plan from analyze context;
- current-view summaries match CLI QueryRecipe results;
- published and current-view scopes are unambiguous in HTML and evidence UI;
- `shareSafe` is returned only when every publishing condition passes;
- Chromium and WebKit `file://` E2E suites pass;
- Skill guidance uses the trusted workflow;
- static and recurring report workflows continue to pass existing verification and rendering tests.
